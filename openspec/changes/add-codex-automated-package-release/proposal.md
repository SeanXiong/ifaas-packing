## 为什么

当前 Codex、GitLab 构建监控和 IFAAS 打包平台相互独立，用户需要手工查找打包项目与版本、切换服务分支、等待构建、提交打包并获取 Seafile 地址。需要建立一条面向单用户桌面的可靠发布链路，让 Codex 在用户明确要求打包时完成目标发现和二次确认，再由现有构建平台持久化执行分支切换、构建监控、自动打包和结果通知。

## 变更内容

- 为系统 B 现有项目、版本、服务和 Git 分支接口增加公共客户端，并同时提供只读 CLI 与本地 STDIO MCP，使 Codex 能实时发现真实候选而不猜测业务 ID。
- 在 Codex 中增加明确打包意图触发、候选选择和发布方案二次确认；用户未明确要求打包时不得登记发布任务。
- 由构建平台接收确认后的精确发布方案，保存本地发布任务，并立即将系统 B 所选服务切换为当前 Git 分支；分支修改不考虑其他用户覆盖，后续失败也不自动恢复。
- 由构建平台精确等待目标 Commit SHA 的 GitLab Pipeline，构建成功后才调用系统 B 自动打包接口。
- 为系统 B 新增异步自动打包任务 API：创建时返回唯一 `taskId`，支持 `clientRequestId` 幂等、按 `taskId` 查询、后台打包和 Seafile 上传，并以本地文件持久化任务状态。
- 系统 B 每日清理创建时间超过 7 天的自动打包记录，不区分任务状态；不删除 Seafile 云端文件和手工打包记录。
- 在构建平台展示提交、分支切换、构建、打包、上传和完成工作流，并复用 Windows Toast 将 Seafile 地址回推电脑。
- 第一阶段保持单用户、本地桌面架构，不新增独立 Java 编排服务、MySQL、多用户管理后台或独立桌面 Agent。

## 能力

### 新增能力

- `package-target-discovery`：通过系统 B CLI/MCP 查询项目、版本、服务和 Git refs，匹配当前仓库并生成真实候选发布目标。
- `codex-release-confirmation`：仅在明确打包意图下准备发布方案，要求用户选择并确认后才向构建平台登记任务和推送代码。
- `automated-package-task`：系统 B 以唯一任务 ID 异步完成打包和 Seafile 上传，提供精确查询、幂等、本地文件持久化及 7 天清理。
- `release-workflow-orchestration`：构建平台持久化发布计划、切换系统 B 服务分支、精确监控 Commit SHA、触发自动打包并保存最终结果快照。
- `desktop-release-tracking`：在桌面构建平台展示发布工作流，并通过 Windows Toast 通知成功、失败和 Seafile 地址。

### 修改的能力

- 无。当前规划仓库没有已归档的对应基础规格；构建平台现有 GitLab 监控和 Windows 通知能力作为外部既有能力复用。

## 影响

- 系统 B 后端：新增自动打包任务创建、查询、幂等、本地文件存储、Seafile 集成和定时清理；继续复用现有项目、版本、服务、refs、Git 配置和模块更新接口。
- 系统 B 本地集成层：新增共享 HTTP 客户端、CLI 与 STDIO MCP，对返回字段进行结构化裁剪和敏感信息过滤。
- 构建平台 `GitLabBuildWatch`：新增发布任务状态机、系统 B 分支修改客户端、自动打包客户端、结果快照、恢复逻辑、工作流展示和发布通知。
- Codex：新增明确意图触发、目标发现、用户确认、发布登记和 `READY_TO_PUSH` 后推送规则。
- 数据：系统 B 继续使用本地文件；构建平台继续使用本地 SQLite。双方通过 `releaseTaskId`、`clientRequestId` 和 `packageTaskId` 建立关联。
- 仓库边界：本 change 存放在 `ifaas-packing` 作为跨系统规划事实源；系统 B 后端与构建平台的实际代码修改必须在各自仓库中按任务拆分实施。
