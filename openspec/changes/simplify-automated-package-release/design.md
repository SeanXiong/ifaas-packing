## 背景

当前 `ifaas-packing` 是打包平台 Web 与 Python 代理，已经能够查询项目、版本和服务，修改服务分支，提交安装包或升级包，并在离线包缺少云盘地址时单独触发 Seafile 上传。现有 `add-codex-automated-package-release` 规划引入了 Codex 逐次搜索和确认项目、版本、服务，以及由构建平台修改打包平台分支的较重编排。

新的约束是：只有用户显式调度 `$ifaas-release` 才打包；打包平台集中配置一个项目和一个产品，其中产品就是现有版本实体；打包平台负责服务发现、分支校准、打包、上传和补偿；构建平台只负责目标 Commit 构建衔接、结果快照和 Windows 通知。第一阶段使用 Skill、CLI/HTTP 和现有平台 API，不依赖 MCP。

该变更跨越三个部署边界：Codex 所在电脑、Windows 构建平台和服务器端打包平台。Codex 会话不能作为长时间任务执行器，因此所有构建、排队、打包和上传状态必须由两个平台持久化。

## 目标与非目标

**目标：**

- 只在用户显式调用 `$ifaas-release` 后建立自动发布任务，消除普通提交或自然语言误触发。
- 由打包平台通过右上角设置抽屉集中维护有效的 `projectId` 与 `versionId`。
- 构建平台精确等待已登记完整 Commit SHA 的 Pipeline，成功后只创建一次打包任务。
- 打包平台在固定项目和版本中按规范化 Git URL 唯一定位服务，持久化排队并串行处理同一服务。
- 打包平台自动校准目标分支、完成组合打包上传，并在云盘地址缺失时执行一次补偿上传。
- 构建平台在进程重启和打包记录清理后仍能展示最终结果并发送 Windows 通知。

**非目标：**

- 不引入 MCP 作为第一阶段依赖。
- 不根据普通自然语言自动启用发布流程。
- 不让用户逐次选择项目、版本或服务。
- 不建设完整配置修改历史，只保留创建者与最后修改者。
- 不审计构建 Commit、打包前 Commit 或制品 Commit 的一致性。
- 不在任务结束后恢复服务原分支。
- 不在第一阶段提供运行中取消、回调推送或多项目多版本路由。
- 不把外部系统后端实现混入当前前端/代理仓库；实际代码仍分别在所属仓库交付。

## 决策

### 采用“显式 Skill 触发、构建平台衔接、打包平台执行”的边界

```text
$ifaas-release
  │ 读取 repositoryUrl、branch、commitSha 和打包参数
  ▼
构建平台
  │ 持久化 releaseTask，等待精确 Commit Pipeline
  ▼
打包平台
  │ 读取固定配置，排队、校准分支、打包、上传、返回结果
  ▼
构建平台
  │ 保存结果快照并发送 Windows 通知
```

Skill 只负责短时、确定性的本地准备和任务登记。构建平台不理解项目目录，也不修改服务分支；打包平台不监控 GitLab，也不发送 Windows 通知。相较让每个组件调用多个低层接口，该边界使重试和恢复归属于真正拥有状态的一方。

### 显式调用是唯一意图门禁，第一阶段使用 CLI/HTTP 而非 MCP

安装后的 Skill 只在用户输入 `$ifaas-release` 时加载完整流程。普通修改、提交、推送，甚至未显式调用 Skill 的自然语言“打包”描述，都不得登记任务；可提示用户显式调用 Skill。

Skill 通过本地 CLI 或受控脚本调用构建平台 HTTP API，凭据从环境变量、受限配置或 Windows Credential Manager 读取，不进入模型参数和日志。MCP 可在后续包装同一客户端和 API，但不是本 change 的交付依赖。

### 推送前登记与完整 Commit SHA 绑定的发布任务

Codex 完成本地检查与 commit 后，先调用构建平台注册 `releaseTask`，再执行 `git push`。任务至少保存 `clientRequestId`、GitLab Project、`repositoryUrl`、branch、完整 Commit SHA 和打包参数。构建平台返回任务已持久化并进入 `READY_TO_PUSH` 后才允许推送。

先登记可避免快速 Pipeline 在任务建立前完成。推送失败时任务进入 `PUSH_FAILED`，不得创建打包任务。构建平台以 `clientRequestId` 幂等返回同一 `releaseTaskId`。

### 打包平台集中保存一个项目和一个版本

打包平台 Header 在用户菜单左侧增加配置状态与“设置”按钮，参考构建平台采用约 460px 的右侧抽屉。抽屉包含“项目”和“产品”两个支持输入匹配的级联 Combobox；界面使用“产品”业务文案，接口和存储统一使用真实实体字段 `versionId`。

项目选择支持分页远程搜索。选择项目后才能查询该项目的版本；项目发生变化时立即清空原版本。输入文本只作为搜索条件，必须选择真实候选后才能保存。服务端保存前重新验证项目存在、版本存在且版本属于项目。

配置保存：

```json
{
  "projectId": 1001,
  "projectName": "AI打包项目",
  "versionId": 2001,
  "versionName": "深海",
  "createdBy": "admin",
  "createdAt": "...",
  "updatedBy": "admin",
  "updatedAt": "..."
}
```

首次创建同时设置创建和修改字段；后续保存保留创建字段，仅刷新修改字段。不建设完整历史表。自动任务创建时复制配置快照，后续修改只影响新任务。配置缺失或失效时拒绝自动任务，并在 Header 显示未配置或失效状态。

### 在固定版本中按 Git URL 确定性发现服务

打包平台读取任务 `targets` 中每个 `repositoryUrl`，与配置版本下每个服务的 `git_url` 规范化后精确比较，兼容 HTTP、HTTPS、SSH 和 `.git` 后缀差异。服务名称相似度不参与选择。

匹配结果必须为唯一服务：零个返回 `SERVICE_NOT_FOUND`，多个返回 `SERVICE_TARGET_AMBIGUOUS`。任务保存解析后的项目、版本、服务和 Git 快照，后续不因设置变化重新选目标。

### 自动任务使用异步 API、两级幂等和可恢复状态

打包平台提供创建和精确查询接口。创建立即生成唯一 `packageTaskId`、原子持久化请求与目标快照，再返回 `202 Accepted`。构建平台使用 `releaseTaskId` 作为打包平台 `clientRequestId`；响应丢失时重试同一键只能得到原 `packageTaskId`。

建议主状态：

```text
ACCEPTED → LOCATING_TARGET → QUEUED → ALIGNING_BRANCH
         → PACKAGING_AND_UPLOADING
         → VERIFYING_CLOUD_RESULT → SUCCESS
```

补偿路径为 `RECOVERING_CLOUD_UPLOAD`；任一不可恢复错误进入 `FAILED`。状态和真实阶段必须持久化，进程重启后从非终态阶段幂等恢复。

### 同一版本服务采用持久化 FIFO 队列和独占锁

锁键固定为 `versionId:serviceId`。同一键任务按创建顺序排队，任务响应暴露 `queuePosition` 和等待时间。队列、锁所有者和任务阶段必须持久化，进程重启后不得并行恢复两个同键任务。

锁覆盖分支校准和会读取服务分支的包生成过程。根据当前打包页面的调用逻辑，锁保守持有至组合打包请求结束并查询到本次新增制品记录；取得记录后释放服务锁。独立云盘补偿只使用制品路径，在释放服务锁后执行。

### 分支不一致自动校准且不恢复原分支

持锁任务先验证目标 branch 存在，再读取服务完整数据和目标 Git 配置。当前分支不一致时查询目标 `git_id`，提交完整模块更新并重新查询验证；已一致则跳过更新。校准失败进入 `BRANCH_ALIGNMENT_FAILED`，不得打包。

任务保存 `previousBranch`、`targetBranch`、`changed` 和 `verified`。后续成功或失败均不恢复原分支，避免引入跨任务回滚竞争。

### 打包平台不执行 Commit 审计

构建平台仍使用完整 Commit SHA 精确等待目标 GitLab Pipeline，这是发布触发门禁，不属于打包结果审计。目标 Pipeline 成功后，构建平台只向打包平台传递仓库、branch 和打包参数；打包平台不接收、查询或保存任何 Commit 审计字段，也不生成 Commit 一致性警告。

打包结果仅归属于持久化发布任务和 `packageTaskId`。系统以目标 branch 完成服务发现、分支校准和打包，不声明最终制品与某个 Commit SHA 一致。

### 优先使用组合打包上传，云盘地址缺失时补偿一次

当 `uploadCloud=true` 时，打包平台在原打包请求中直接启用现有云盘上传选项，不在正常路径二次调用上传。第一阶段直接沿用当前页面逻辑：以新增记录的 `download_path` 或 `storage_path` 判断制品已生成，以 `seafile_path` 判断云盘成功，暂不依赖完整 `pack_status` 枚举。存在 `task_id_2seafile` 且上传未完成时继续等待；没有进行中上传且地址仍缺失时，使用稳定键 `packageTaskId:cloud-recovery` 在本地保证只调用现有独立上传能力一次。

补偿后再次查询仍无地址则进入 `CLOUD_ADDRESS_MISSING`。`uploadCloud=true` 的成功不变量是包成功且至少存在一个可用云盘地址；`uploadCloud=false` 时包成功即可完成。在线包不支持云盘上传的既有约束在创建阶段校验。

### 构建平台轮询、保存快照并通知，不使用服务器回调

桌面构建平台通常不可被服务器主动访问，因此第一阶段保存 `packageTaskId` 并有界轮询打包平台。终态时保存解析目标、分支变化、包名称、下载地址、云盘路径、云盘链接和 MD5。之后停止轮询，即使打包平台清理任务记录仍从本地快照展示。

成功和失败均发送一次 Windows Toast；成功且存在 `cloudUrl` 时支持点击打开。通知失败单独记录，不改变已经成功的发布主状态。

## 风险与权衡

- [自动切换服务分支会影响手工打包或其他用户] → 同一版本服务使用持久化 FIFO 锁；第一阶段接受平台外部人工修改仍可能发生，不实现分支租约和自动恢复。
- [不执行 Commit 审计，制品不能证明对应构建 Commit] → 构建平台仍精确等待目标 Pipeline，但产品明确按目标 branch 打包，页面和通知不得宣称制品与某个 Commit SHA 一致。
- [组合上传完成与云盘地址写回存在短暂延迟] → 先查询进行中上传并执行有界等待，确认缺失后才进行一次幂等补偿，避免重复文件。
- [缺少后端源码，无法确认打包引擎最后一次读取服务分支的时点] → 按当前页面调用链保守持锁到打包请求返回并发现新增制品记录。
- [持锁范围过长降低吞吐] → 包文件生成后不再依赖分支时立即释放锁，让上传和下一任务并行。
- [全局配置被任意已登录用户覆盖] → 保存创建人、最后修改人和时间并在任务中固化快照；第一阶段不建设角色权限和完整历史。
- [历史实现残留与新 change 行为冲突] → 已移除旧规划文件，并停用旧方案中未完成的项目/版本逐次选择、构建平台切分支和 MCP 门禁任务，以本 change 作为唯一事实源。
- [外部系统真实 API 字段尚未完全确认] → 在各所属仓库先做契约盘点和非生产样例验证，再实现状态机和 DTO。

## 迁移计划

1. 以当前部署页面已使用的项目、版本、服务、refs、模块更新、组合打包上传、独立 Seafile 上传及进度查询接口为兼容基线，并采用保守锁释放点。
2. 交付类型化自动打包设置接口及右上角设置抽屉，完成项目与产品级联选择和配置校验。
3. 交付打包平台自动任务文件/数据模型、幂等创建查询、FIFO 队列、服务锁、分支校准和云盘补偿。
4. 在构建平台交付发布任务登记、精确 Commit Pipeline 衔接、打包客户端、轮询恢复、结果快照和 Windows 通知。
5. 简化 `ifaas-release` 插件为显式 Skill 与 CLI/HTTP 工作流，在非生产项目完成端到端验收。
6. 禁用旧方案未完成的冲突入口，再逐步启用新自动发布链路；保留现有 Web 手工打包作为回退路径。

回滚时禁用 `$ifaas-release` 发布登记和构建平台自动调用，保留打包平台配置与任务记录用于审计，继续使用现有手工打包页面。新接口均为增量能力，不改变手工打包请求。
