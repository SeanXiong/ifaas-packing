## 为什么

现有自动发布规划需要 Codex 逐次发现并确认项目、版本和服务，且把分支切换、打包与上传职责分散在多个组件中，导致映射和编排过重。现在需要以打包平台固定配置为事实源，通过显式 Skill 触发、确定性服务匹配和异步任务，把“构建成功后自动打包并返回云盘地址”收敛为可恢复、可审计的稳定链路。

## 变更内容

- 仅在用户显式调用 `$ifaas-release` 时登记自动发布任务；普通修改、提交、推送和自然语言打包描述不自动触发。
- 在打包平台 Header 右上角增加“设置”入口，参考构建平台使用右侧抽屉，以支持输入匹配的级联下拉框配置固定项目和产品；产品复用现有版本实体，持久化 `projectId` 与 `versionId`。
- 配置只保留创建人、创建时间、最后修改人和最后修改时间；自动任务创建时保存项目与版本名称、ID 快照，后续配置修改不影响已创建任务。
- Codex 在推送前向构建平台登记与完整 Commit SHA 绑定的发布任务；构建平台仅等待该 Commit 的 GitLab Pipeline，成功后调用打包平台自动任务 API。
- 打包平台按已配置项目和版本遍历服务，以规范化 Git URL 唯一匹配当前仓库；无匹配或多匹配时返回结构化失败。
- 打包平台按 `versionId + serviceId` 对自动任务持久化 FIFO 排队并加锁，完成分支校准和包文件生成后释放锁。
- 打包时直接使用现有“打包并上传云盘”组合能力；当要求上传云盘但最终缺少云盘地址时，确认没有进行中的上传后执行一次幂等补偿上传。
- 构建平台按 `packageTaskId` 轮询结果，保存包名称、下载地址、云盘路径、云盘链接和 MD5，并发送 Windows 通知。
- 第一阶段不依赖 MCP、不支持运行中取消，也不建设完整配置修改历史。

## 能力

### 新增能力

- `package-automation-settings`：在打包平台配置和校验全局自动打包项目与版本，并提供右上角设置抽屉、可搜索级联选择和配置状态展示。
- `deterministic-package-orchestration`：由打包平台确定性定位服务、持久化排队和加锁、校准分支、组合打包上传及补偿缺失云盘地址。
- `explicit-release-skill-trigger`：仅通过显式 `$ifaas-release` Skill 收集本地 Git 上下文、登记发布任务并在平台准备完成后推送代码。
- `build-package-coordination`：构建平台持久化精确发布意图、跟踪目标 Commit Pipeline、调用并轮询打包任务、保存结果快照和发送 Windows 通知。

### 修改的能力

- 无。当前规划仓库没有已归档的对应基础规格；`add-codex-automated-package-release` 旧规划文件已移除，本 change 作为简化方案的唯一事实源。

## 影响

- 打包平台前端：调整 Header，新增设置按钮、配置状态标签、右侧设置抽屉、项目搜索和版本级联搜索。
- 打包平台服务端：新增类型化配置查询/保存接口、项目与版本候选接口、自动任务创建/查询、配置与任务快照、FIFO 队列、服务锁、分支校准、组合打包上传和补偿上传编排。
- 构建平台 `GitLabBuildWatch`：新增发布任务登记、精确 Commit Pipeline 跟踪、打包任务调用与轮询、结果快照和 Windows 通知。
- Codex 插件：简化为显式 Skill 与本地 CLI/HTTP 调用，不依赖 MCP，不再让用户逐次选择项目、版本或服务。
- API：新增构建平台发布任务接口和打包平台自动任务、设置、候选查询接口；所有创建与补偿操作均使用稳定幂等键。
- 数据：打包平台保存全局目标配置和自动任务状态；构建平台保存发布工作流及最终制品快照。
